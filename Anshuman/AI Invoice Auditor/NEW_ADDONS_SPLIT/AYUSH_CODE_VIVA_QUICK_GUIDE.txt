       |

       |

       |

6. TABLES - SIR RELATIONSHIP PUCHHE TOH
---------------------------------------
ERP schema:
  vendors -> approved vendor details.
  sku_master -> recognised items.
  purchase_orders -> PO header, vendor_id references vendors.
  po_line_items -> PO items, po_number references PO, item_code references SKU.

Audit schema:
  invoice_audit -> invoice header/text/status/checksum/current extraction.
  invoice_line_items -> invoice_id references invoice_audit.
  discrepancies -> findings linked by invoice_id.
  human_feedback -> correction/review entries linked by invoice_id.

Primary key identifies row. Foreign key links valid related records.
UNIQUE file_checksum prevents multiple current rows for identical file bytes.
Upsert means insert new or update matching existing key; not a historical snapshot.
Raw text/JSONB extraction and structured numeric columns have different purposes.
Database NUMERIC doesn't mean calculations in Python are Decimal; here float used.

7. CONFIG + BUSINESS CASES (QUICK VIVA)
---------------------------------------
Price tolerance: 5%, condition strictly > tolerance in graph comparison.
  ERP 100, invoice 105: at threshold; no price finding from that condition.
  ERP 100, invoice 110: 10% deviation -> WARNING in this graph function.
  ERP 100, invoice 120: 20% deviation -> ERROR in this graph function.
Quantity tolerance: 0%; any nonzero deviation for positive ERP qty -> ERROR.
PO missing/unrecognised: CRITICAL.
Vendor ID mismatch: ERROR if invoice vendor ID supplied and differs from PO.
Currency mismatch with vendor reference: ERROR.
Unknown master SKU: WARNING; item absent from PO: ERROR.

Do not predict final workflow solely from these examples: delegated MCP business
validation can add differently named/severity findings. These are graph examples.

8. REPORT RESULT - THREE WORDS ALAG HAIN
----------------------------------------
validation_status:
  no findings/data errors -> passed;
  only lower-severity findings -> partial;
  ERROR/CRITICAL or data errors -> failed.
recommendation:
  passed + confidence >=0.95 -> approve;
  failed + field_name currency OR missing mandatory header -> reject;
  otherwise -> manual_review.
review_status:
  new risk gate/reviewer decides auto_approved, pending_review, approved, rejected.
These are not interchangeable. Automatic recommendation is not payment authority.

12. RAPID QUESTIONS
--------------------
Why Mock ERP? -> controlled enterprise reference without real SAP/Oracle access.
Why not LLM comparison alone? -> approved facts and numerical rules authoritative hain.
Why API? -> reference-service boundary; callers need response contract, not SQL schema.
Why Pydantic? -> expected request/response data structure and type validation.
Why parameterized SQL? -> user-supplied values SQL text se separate bind hote hain.
Why JSON fallback? -> local demo continuity, but active backend disclose karna hai.
Why discrepancies? -> explainable field-level actual vs expected result.
Why separate audit schema? -> evidence/results and approved master data have distinct roles.
Is mismatch fraud? -> not necessarily; wrong extraction, billing error or genuine change possible.
Is A2A ERP HTTP? -> no. A2A delegates agent work; tool uses HTTP to reach Mock ERP.
Is RAI same as ERP rejection? -> no. RAI guards trust boundaries; ERP validation checks business facts.
