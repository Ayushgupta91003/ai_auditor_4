3. THE BASICS YOU SHOULD BE ABLE TO EXPLAIN
-------------------------------------------
LangGraph: ordering and routing of shared state through a graph.
Google ADK: framework for a model-driven tool-using agent/runner/session.
A2A: exchange of requests/results for another agent's advertised skill.
AgentCard: metadata explaining name, framework, URL, skills and capabilities.
Skill: callable business capability, e.g. translate_invoice.
Message: text/data parts plus context identity.
Task: execution status and returned artifact(s).
Artifact: structured output returned by the task, not necessarily a file.

This is application-role separation. Both frameworks can live inside ONE agent
container. Cross-framework does not require a new Docker service per role.

5. TRANSLATION WALKTHROUGH
---------------------------
workflow.translation_node(state)
  -> a2a_client.try_send('translation-agent','translate_invoice',{'text':raw})
  -> A2A message/send envelope
  -> A2ARegistry selects the registered agent and skill
  -> TranslationAgent.execute()
  -> run_with_adk() when possible
  -> ADK LlmAgent/Runner with LiteLlm(BEDROCK_MODEL)
  -> lang_bridge FunctionTool wrapper -> MCPClient.call('lang_bridge')
  -> authoritative tool result, parsed into state.

Agent instruction says to call the tool, not translate invented facts from
memory. run_with_adk() expects usable JSON with translated_text. An unusable
result triggers fallback rather than assuming free-form text is correct.

This is your handover point to Aman: 'ADK selects/calls a capability; MCP exposes
and invokes its implementation.'

6. BUSINESS VALIDATION WALKTHROUGH
-----------------------------------
workflow.business_validation_node(state)
  -> business-validation-agent / validate_against_erp
  -> ADK tools business_validation and erp_lookup
  -> approved ERP records via the tool's HTTP path
  -> discrepancies merged into current state.

The ordinary graph validator already runs first. This delegated route is an
additional validation path, not the first or only one. Deduplication is by
field_name and invoice_value; differently named equivalent findings can remain.
Single-record lookup is a direct tool path rather than unnecessary reasoning.

7. WHAT ADKAgent._build() CREATES
----------------------------------
LlmAgent: agent instruction, tools and LiteLlm model adapter.
FunctionTool: exposes an MCP-calling Python wrapper to ADK.
InMemorySessionService: per-agent conversational session store.
Runner: drives one turn and reads final-response events.

google.genai.types is used for message objects. That import does not mean Gemini
is the selected model: intended model selection is the Bedrock LiteLlm string.
Session memory is not the audit DB and not durable LangGraph checkpoints.

8. A2A TRANSPORT IN THIS CODE
------------------------------
A2A_BASE_URL empty -> direct in-process custom server/registry dispatch.
A2A_BASE_URL set -> HTTP JSON-RPC to /a2a/{agent_id}.
Discovery: /a2a/agents and /a2a/{agent_id}/.well-known/agent-card.json.
Invocation: JSON-RPC method message/send, skill metadata and Message data.
Server also offers tasks/get using bounded in-memory task retention.

Conceptual example envelope (illustrative, not a credential-bearing command):
  method: message/send
  params.skill: translate_invoice
  params.message: data part containing the document text
Result: Task with status completed and translation artifact data.

Client get_card()/supports() can inspect skills. send() does not enforce a
separate discovery request on every call. Do not promise a network discovery
round trip for the default in-process route.

9. FALLBACKS AND THE EVIDENCE YOU MUST SHOW
-------------------------------------------
ADK build is optional and checks ADK_ENABLED plus explicit model credentials.
If unavailable, execute() calls run_deterministic(), often through the same MCP
tool. Returned executor can be google_adk or deterministic_tool_call.
A2A failure can also return control to a local workflow translator.

The underlying LLM wrapper may itself fall back from Bedrock to local regex/
passthrough handlers. Thus even a successful task needs execution-mode context.
This code uses direct LiteLLM Bedrock, NOT ChatBedrockConverse initialization.
Custom a2a/*.py is not proof of official A2A SDK conformance/authentication.

11. VIVA QUESTIONS
-------------------
Q: What did you add, since LangGraph already existed?
A: A second framework's agent execution and a discovery/delegation boundary.
Q: Why not directly call a translation function?
A: Named skill delegation separates orchestration from the agent implementation.
Q: MCP versus A2A?
A: MCP invokes tools; A2A delegates work to agent capabilities.
Q: Why only six containers if there are seven agents?
A: Logical agent roles share the agent service; deployment and role counts differ.
Q: What happens on ADK failure?
A: The registered agent can call its MCP tool deterministically, or workflow
   fallback can take over; executor/mode exposes the distinction.
Q: Is the communication automatically secure?
A: No. This custom protocol layer is not complete authentication/TLS.
Q: Does SDK installation prove execution?
A: No. An actual runner turn and output/executor evidence is required.
