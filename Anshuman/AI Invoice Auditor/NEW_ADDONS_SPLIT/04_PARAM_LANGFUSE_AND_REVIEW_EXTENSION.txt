3. TRACE, SPAN, GENERATION AND SCORE
------------------------------------
Trace: one logical run, such as an invoice audit or RAG question.
Span: one step inside that run, such as MCP invocation or retrieval.
Generation: a model-generation observation with model/prompt/output metadata.
Score: an attached metric, such as context_relevance or average triad score.
Session/user/tag metadata helps group related operations; it is not an
authenticated employee identity or guaranteed durable business state.

Audit database answers 'what invoice/result was stored?'
Observability answers 'which path ran, how long, what failed, what was reused?'
Neither replaces the other. A nice trace is not proof the numerical audit was
correct or that required source data was complete.

4. OBSERVABILITY FACADE
------------------------
get_client() reads configured Langfuse public/secret keys and base URL/host,
initializes a compatible SDK client and tracks initialization status/errors.
status() exposes flags and API mode without requiring a secret-value display.
trace(), span(), record_generation() and observe() isolate calling modules
from differences in SDK interfaces.

Modern SDK path uses current observation contexts. Legacy path can track
parents with ContextVar and explicit trace/span objects. _TraceRecorder and
_SpanRecorder let callers set outputs/failures; trace recorder can attach scores.
_flush() helps export queued observations.
If unconfigured/unavailable, operations can degrade to structured logs.
Successful application processing therefore does not prove cloud export.

8. WORKING REVIEW EXTENSION - EXACT ORDER
------------------------------------------
The normal processing graph is reporter -> risk_gate -> optional indexing.
Pending records appear in GET /review/queue and the Human Review tab.

Revalidate with Edits:
  _rebuild_state(invoice_id)
    -> apply allowed header changes and optional full replacement line list
    -> validator_node()
    -> reporter_node()
    -> compute_risk()
    -> force review_status='pending_review'
    -> record_correction(revalidated=True).

The pasted reference PPT showed validator -> risk_gate -> reporter. Correct
that order in the new explanation. The revalidation endpoint is not literally
the same full eight-node graph again, and it does not perform every extra

Approve & Index:
  indexing_node -> update approved -> record_review_decision.
Reject:
  update rejected -> record_review_decision; no explicit removal of old vectors.
Feedback-only:
  INSERT feedback without applying/revalidating it.

12. VIVA QUESTIONS
-------------------
Q: How is observability different from the audit trail?
A: Audit stores business facts/decisions; traces expose execution path/timing/errors.
Q: What is a span?
A: One nested operation in a larger logical trace.
Q: Does a self-test generation prove Bedrock ran?
A: No, its model is n/a and the data is synthetic ping/pong.
Q: Can the app work without Langfuse?
A: It can fall back to logs, but then cloud tracing was not demonstrated.
Q: Is basic HITL new?
A: No. Actual optional revalidation implementation and explicit risk-gated
   approval controls extend the old baseline.
Q: Is every original extraction immutable here?
A: No. Current structured state is upserted; feedback records retain changes.
Q: Does a successful approval always mean vectors were stored?
A: Inspect rag_indexed/backend result; approval status alone is insufficient.
Q: Are trace payloads automatically anonymous?
A: No. Truncation and selective guardrails are not universal anonymization.
