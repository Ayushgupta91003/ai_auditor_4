7. DATA VALIDATION VS BUSINESS VALIDATION
-----------------------------------------
File: services/agent/graph/nodes/validator.py

_resolve_vendor_id(): vendor name/details se reference ID resolve karne ki help.
run_data_validation(): required header/line fields, currency aur arithmetic ki
  checks. Question: "Invoice apne andar complete aur consistent hai kya?"
run_business_validation(): PO/vendor/SKU reference se quantity, price, currency
  aur item membership compare. Question: "Approved purchase se match hai kya?"
validator_node(): checks run karke errors/discrepancies workflow state mein deta hai.

Data example: quantity 10 x price 100, lekin line total 900 -> internal issue.
Business example: 10 x 110 = 1100 correctly calculated, approved price 100 ->
ERP mismatch. Dono validations alag reasons se zaroori hain.

Normal reference access HTTP hai. Current validator mein HTTP exception par
direct ERPDatabase fallback bhi hai. Isliye viva mein "every path strictly
HTTP-only" mat claim karna. Normal service separation HTTP se hoti hai.

8. RULES AUR CALCULATION - EK EXAMPLE
------------------------------------
File: config/rules.yaml
Required headers: invoice_number, invoice_date, vendor_name, currency, total_amount.
Required line fields: item_code, description, quantity, unit_price, line_total.
Price tolerance 5%; quantity tolerance 0% (exact match expected).

Deviation % = abs(invoice value - ERP value) / abs(ERP value) x 100.
Approved price 12, billed 15 -> 3/12 x 100 = 25% -> price discrepancy.
Approved quantity 50, billed 51 -> 1/50 x 100 = 2% -> quantity discrepancy.
ERP USD, invoice EUR -> currency discrepancy, even though both ISO codes exist.
Missing PO -> reference cannot be verified; current graph flags CRITICAL.

Graph price check uses strictly greater than tolerance. Exactly 5% is within
that comparison boundary. Graph path: >5% up to 10% WARNING; >10% ERROR.
Zero ERP references have special limitations: some comparisons only run for
positive ERP values. Don't claim the formula handles every zero case universally.

Current graph also has an ADK/A2A business-validation route using the MCP tool;
severity details differ across those routes. Above severity example is specifically
run_business_validation() in graph/nodes/validator.py, not a universal promise.

9. DISCREPANCY KA MATLAB
------------------------
Ek discrepancy = ek recorded mismatch, including:
field_name, invoice_value, erp_value, deviation_pct, severity.
Example: unit_price_SKU-001 | 15.00 | 12.00 | 25% | ERROR.
Isse reviewer ko sirf "failed" nahi, actual problem aur expected value dikhte hain.
Discrepancy automatically fraud prove nahi karti; correction/review needed ho sakta hai.

10. REPORTING - RESULT KAISE BANTA HAI?
--------------------------------------
File: services/agent/graph/nodes/reporter.py
generate_html_report(): readable HTML report banata hai.
reporter_node(): findings se validation status/recommendation derive karta hai,
JSON/HTML outputs banata hai aur database persistence invoke karta hai.

validation_status: passed / partial / failed.
recommendation: approve / manual_review / reject.
Current reporter mein failed + currency mismatch ya missing mandatory header
reject recommend kar sakta hai. Har discrepancy ka result reject nahi hota.
Passed invoice ke approve recommendation mein translation confidence >=0.95 bhi hai.

recommendation advisory result hai. review_status operational routing/decision hai.
Approve recommendation ko bank payment instruction mat bolo.

11. AUDIT DATABASE - ERP DATABASE SE KAISE DIFFERENT?
----------------------------------------------------
File: services/agent/utils/db.py; class AuditDatabase.
ERP tables = approved reference. Audit tables = invoice evidence + checks + review.

is_checksum_audited(): same file bytes ka checksum already processed hai kya?
insert_invoice_audit(): current invoice header/evidence/status insert/upsert.
insert_line_items(): invoice ke current structured items save/replace.
insert_discrepancies(): findings save; nonempty updates replace existing findings.
insert_human_feedback(): user correction feedback record.
list_invoices(): dashboard history list.
get_invoice_details(): selected invoice + associated details.
update_review_status(): risk/review state update.
record_review_decision(): reviewer decision record.
record_correction(): correction details/history entry record.

Key tables: audit.invoice_audit, invoice_line_items, discrepancies, human_feedback.
Current implementation has local SQLite support as well; lab main store PostgreSQL.
LangGraph checkpoints track workflow progress; they are not ERP master records.

Important: current rows/report files can be overwritten/upserted. Feedback is
recorded, but full immutable historical extraction/report versions are NOT provided.
Empty line/discrepancy lists have early-return edge cases; don't claim all stale
rows are always cleared. Current Python calculations use float, not Decimal-only.

   karne ke liye controlled reference service banayi hai.

A. ERP approved facts deta hai; LLM extraction/language tasks mein help karta hai.

   API contract se integration clear hoti hai aur real ERP adapter future mein possible hai.
Q. SKU master aur PO line difference?
A. SKU master batata hai item recognised hai. PO line batati hai us order mein
   woh item, kitni quantity aur kis price par approve hua tha.
Q. Record nahi mila toh?
A. Lookup API 404; validator relevant missing-reference finding bana sakta hai.
Q. Exactly 5% price mismatch?
A. Graph price condition > tolerance hai, so exactly 5% us check se flag nahi hota.
Q. DB down ho toh?
A. Mock ERP JSON fallback use kar sakta hai. Active backend check karenge;
   PostgreSQL persistence successful assume nahi karenge.
Q. Reject aur pending_review dono kyon?
A. Reject system recommendation hai; pending_review human decision ki state hai.
Q. Old vs new mein tumhara contribution kya explain karoge?
A. Baseline ERP comparison pehle se tha; new allocation RAI/risk routing hai.
   Ownership discussion mein actual group work ke hisaab se bolunga.
