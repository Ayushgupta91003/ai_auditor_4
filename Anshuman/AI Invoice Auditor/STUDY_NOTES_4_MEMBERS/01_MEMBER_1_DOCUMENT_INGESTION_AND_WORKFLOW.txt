3. HOW A DOCUMENT ENTERS THIS VERSION
------------------------------------
The main automatic route is a bind-mounted incoming folder. A daemon thread
polls that directory. The default poll interval is four seconds; main.py can
read WATCHDOG_POLL_INTERVAL. main.py starts the watchdog in its lifespan and
stops it on shutdown. API /process can also process a path or scan the folder.

Important: this version is not the old port-8765 Groq upload dashboard.
The friend version uses Streamlit on port 8501 and a folder-based watcher.
Do not assume an upload button from the earlier project exists here.

SUPPORTED_EXTENSIONS includes .pdf, .docx, .doc, .png, .jpg, .jpeg and .tiff.
Support is not equally strong: .doc is passed to python-docx, which normally
expects DOCX. Do not promise reliable legacy binary .doc support.

4. WATCHDOG: STEP-BY-STEP
-------------------------
scan_cycle() lists supported non-hidden files and inspects size and mtime.
If a new file was modified less than 1.5 seconds ago, it waits for another
cycle. If a tracked file changes size/mtime, it marks it unstable and waits.
This reduces the chance of reading a file halfway through a copy; it is a
heuristic, not a file-lock/atomic-upload guarantee.

For a stable file it computes SHA-256 over 65,536-byte chunks. Reading chunks
avoids loading the whole file only to calculate a checksum.

It checks two places:
  a. _seen_files: in-memory state for this watchdog process.
  b. audit_db.is_checksum_audited(): previously persisted file content.

If already audited, it skips the file. Otherwise it calls
run_invoice_audit_pipeline(str(filepath)). It records TRIGGERED, PROCESSED,
SKIPPED or ERROR events and updates counters. Recent events are a deque capped
at 60. Threading.Lock protects shared status/counter access. threading.Event
controls stop and pause. This is polling, not a cloud event queue.

Content identity versus name: a renamed identical file has the same checksum;
a file with changed bytes has a different checksum even if its name is unchanged.
Do not call this business-invoice duplicate detection: two PDFs with the same
invoice number but different bytes can still have different checksums.

5. EXTRACTION ROUTING
---------------------
extractor_node() computes checksum again and checks the database, giving a
second deduplication boundary for calls that bypass the watcher.

PDF:
  pdfplumber attempts embedded-text extraction page by page.
  If that raises an exception, pypdf is tried.
  If text is absent or fewer than 15 characters, ocr_pdf() is attempted.
  ocr_pdf(): pdf2image + Poppler rasterize at 300 DPI; Tesseract reads pages.

DOCX:
  python-docx reads nonempty paragraphs AND table rows.
  Table cells are joined with ' | ' so line-item content is not discarded.

Images:
  PIL opens the image and pytesseract.image_to_string() runs OCR.
  Default OCR_LANGS is eng+spa+deu, configurable through the environment.

The state records extraction_method, raw_extracted_text and any error.
On empty extraction it records an error string; that alone is not a universal
early-stop mechanism for the rest of the workflow.

OCR versus LLM: OCR converts image pixels to text. Translation changes language.
Parsing maps text to fields. They are separate tasks; one does not replace another.

6. SIDECAR METADATA
-------------------
load_metadata() looks for a file with the same stem and .meta.json suffix.
Example: INV_ES_003.pdf -> INV_ES_003.meta.json.
It can carry subject/language hints or email-related metadata.
The parser uses a subject regex to supplement missing PO/invoice numbers.
This is not a live Gmail/Outlook integration: sidecar metadata is input data.

7. NORMAL TRANSLATION CALL CHAIN
--------------------------------
workflow.translation_node(state)
  -> a2a_client.try_send('translation-agent', 'translate_invoice', {'text':raw})
  -> TranslationAgent.execute()
  -> Google ADK Runner, when ADK/model credentials are available
  -> MCP lang_bridge tool
  -> guardrails.scan_document()
  -> translation prompt + LLMClient.completion()
  -> parsed source_language / translated_text / translation_confidence.

Member 4 explains the protocol machinery. You explain the language behavior.
lang_bridge caches by model plus sanitized text through ResponseCache.
Translation result includes whether the cached value was used.

When the ADK runner cannot operate, the same translation agent can directly
invoke the MCP tool deterministically. If the A2A result itself is unavailable
or unusable, workflow.translation_node() calls translator_node(state).
The fallback translator can bypass English translation using metadata and
simple heuristics. A malformed model translation falls back to raw text and
reduced confidence rather than proving a successful English translation.

CRUCIAL LOCAL-MODE DETAIL:
utils/llm_client.py has no real translation model in local mode. It detects
language and passes text through. Non-English text receives confidence 0.0.
Therefore 'application works without keys' does not mean genuine translation
or live Bedrock/ADK reasoning ran. Inspect logs and the executor result.

8. STRUCTURED PARSING
---------------------
parser_node() loads config/prompts.yaml -> parsing system/user templates.
It sends translated_text, falling back to raw text, plus metadata to llm_client.
It strips simple Markdown code fences and calls json.loads().

Expected output includes invoice_number, invoice_date, vendor_id, vendor_name,
po_number, currency, subtotal, tax_amount, total_amount and line_items.
The complete parsed dictionary is also stored as extracted_raw.
Missing invoice/PO identifiers can be supplemented from metadata subject.

JSON is structured syntax, not proof of semantic correctness. A valid JSON
object can contain a wrong currency or amount; Member 2's rules handle that.
This code uses dictionary/TypedDict contracts. It does not enforce every
parsed field through a Pydantic Invoice model as the earlier implementation did.
On parsing exception it records state['error'] and logs a response excerpt.

9. LANGGRAPH FLOW - MEMORIZE THIS ORDER
--------------------------------------
START
  -> extractor
  -> translator        (A2A translation delegate)
  -> parser
  -> validator
  -> business_validation (second, ADK/A2A validation route)
  -> reporter
  -> risk_gate
      -> indexing -> END, only if review_status == 'auto_approved'
      -> END otherwise, awaiting human action.

LangGraph nodes are ordinary functions returning updated state dictionaries.
StateGraph defines ordering and the conditional branch. The graph does not
automatically make every ordinary Python function an autonomous LLM agent.
Some registered A2A agents wrap capabilities; the ordinary main graph also
calls several node functions directly. Avoid saying every node uses MCP.

invoice_id: persisted business identity.
thread_id: workflow/checkpoint identity.
report paths/rag_indexed/error: export, derived index and failure information.

11. CHECKPOINTS AND FALLBACK EXECUTION
-------------------------------------
get_checkpointer() attempts a PostgresSaver with search_path=langgraph.
run_invoice_audit_pipeline() builds thread_id from the source filename stem:
'invoice-' + Path(file_path).stem. This is different from a checksum or UUID.
Different directories with identical stems can share that thread identifier.

The graph is compiled lazily and reused. If checkpointer setup fails it can
compile without persistence. If LangGraph is unavailable, or invocation raises,
the code can run _run_sequential() in the same node order.

Do not promise automatic exactly-once resume: the public function initializes
state and invokes the graph, while its exception fallback reruns sequentially.
A checkpointer being present is not the same as a tested explicit resume API.
The shown main.py has no dedicated old-project /retry endpoint.

14. VIVA QUESTIONS AND SHORT ANSWERS
-------------------------------------
Q: Why checksum?
A: Filename can change; SHA-256 identifies exact bytes for idempotent ingestion.
Q: Why wait for file stability?
A: A poll can see a file while it is still being copied.
Q: What is TypedDict?
A: Python typing for dictionary keys; it is not automatic runtime validation.
Q: Why translation before parsing?
A: A common language simplifies downstream prompts and reference comparisons.
Q: Does confidence 1.0 prove correctness?
A: No. Some paths set it heuristically, and model confidence is not calibrated.
Q: What is LangGraph state?
A: Shared data flowing through ordered/conditional processing nodes.
Q: What if ADK fails?
A: A deterministic MCP-tool path or in-graph translator can run; inspect executor.
Q: Is all processing asynchronous?
A: No. The API handlers and watchdog pipeline are mostly synchronous; the watcher
   uses a background daemon thread and the ADK/session helper has async bridging.
Q: Why keep source text if parsed JSON exists?
A: Audit traceability and derived RAG recovery need original evidence.
